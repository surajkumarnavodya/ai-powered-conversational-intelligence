## SEC-001 — proposed fix (flagged, not applied)

**Why flagged rather than fixed.** Rule 8: changing `/health`'s response
shape is an API-contract and user-visible change. It cannot simply be
put behind auth, because the React app reads it *before* anyone is
logged in — `components/auth/AuthGate.tsx` and `pages/auth/Register.tsx`
read `local_auth_enabled`, `google_signin_enabled` and
`google_client_id` to decide what the login page renders. Gating the
whole endpoint would break sign-in.

**Proposed split:**

- `GET /health` stays public and returns only what an unauthenticated
  client legitimately needs: `status`, and the auth-mode flags the login
  page renders from.
- The operational detail — database names, table counts, Ollama host,
  model names, the remaining feature flags — moves behind the existing
  auth dependency, e.g. `GET /health/detail` requiring a local user.

**Risk if left as-is for UAT:** low in a closed UAT environment on
localhost; meaningful if the UAT host is reachable beyond the test
group, because the endpoint names the real databases and confirms which
optional subsystems are on — useful reconnaissance for a later attempt.

**Decision needed from the product owner:** accept for UAT with a
documented waiver, or take the split before UAT opens.

## Phase 3/4 — decisions needed from the product owner (2026-10-28)

Four findings were deliberately **not** fixed, each because the fix
crosses one of Shared Rule 8's stop lines. Full reasoning and proposed
fixes are in `phase-4-authorization.md` §4; this is the short list.

### `AUZ-002` — S1, and the one that should block UAT sign-off

A tenant's admin can **list, download and delete** another tenant's
documents. Confirmed at runtime, not inferred. The fix needs a
`tenant_id` column on the document and chunk tables, a migration, a
backfill to `DEFAULT_TENANT_ID`, and a **required** (not defaulted)
tenant parameter on five `rag.store` entry points — plus the same work
for `media/store.py`. The "required, not defaulted" detail matters:
CLAUDE.md §5.4 records that `SEC-006`'s optional parameters mean a new
caller silently gets the weaker path.

**Decision:** schedule the migration before UAT, or run UAT
single-tenant and say so in writing. Running multi-tenant UAT on this
code means tenants can read and destroy each other's documents.

### `AUZ-003` — S2

A suspended account in a suspended tenant can still call `POST /ask` and
read `GET /schema/tables` for up to `access_token_expire_minutes`
(default 15). Four options are weighed in §4.2.

**Recommendation:** accept for UAT with the window documented and
`access_token_expire_minutes` left at 15 (it has no upper bound in its
`Field(...)` constraint, so this needs to be a conscious choice), then
take Option B — the check in `api/authz.py` with a short per-process
cache — before production.

### `AUZ-004` — S3

An account whose only role is `platform_admin` is refused on 11 routes a
plain `admin` reaches, because `agent.authz` does not know that role
name. Fail-closed, so not a security hole, but it will present in UAT as
a broken admin account.

**Decision:** grant `platform_admin` in `agent.authz.ROLE_PERMISSIONS`,
or document that the platform-admin account must also hold `admin`. The
second is free and is the safer default; the first changes the
authorization model.

### `AUZ-005` — S3

Any `user` can write a golden example that steers every other user in
their tenant, with no review step. Cannot escalate privilege — the
validator and result gate still apply — so the exposure is to answer
*accuracy*.

**Decision:** accept (it is the thumbs-up feature), or add a review
step, or narrow `GOLDEN_EXAMPLE_WRITE` to `analyst`. Accepting is
reasonable for UAT; it should be a recorded choice rather than a default.

## Phase 7 — context engineering (2026-10-29)

Method and evidence: [`phase-7-context.md`](phase-7-context.md).
**0 S1, 1 S2, 5 S3, 4 S4, 1 unverified.** Five fixed, two flagged.
Full suite **9,543 passed / 0 failed** after the fixes. Verified
end-to-end against the running app: two questions answered correctly on
all four live SQL Server databases, with zero false-positive truncation
warnings and nothing over budget.

### The one theme worth carrying forward

This codebase already understood the failure mode this phase was sent to
look for. `agent/context_budget.py`'s docstring describes Ollama
truncating a prompt from the start and removing the system prompt.
`rag/llm.py`'s docstring describes the same thing happening to RAG and
web prompts. `Settings.web_search_context_max_chars`' comment shows the
arithmetic sized against the window and dates the measurement. All three
are correct, and two of them are better documented than most production
code.

What was missing was the feedback loop. `prompt_eval_count` — the number
that says how much of the prompt the model actually read — has been
logged on every call for as long as `log_ollama_timing` has existed, and
nothing ever compared it to what was *sent*. So **every finding below had
to be measured by hand, and any of them could have been live for months
without leaving a trace.** `CTX-006` closes that and is the most valuable
change in this phase; `CTX-002`, `CTX-004` and `CTX-005` are all things
it would have surfaced on its own.

The second theme is coverage asymmetry, and it is the same shape as
`LOP-003` from Phase 6: a control exists, is correct, and covers some of
the places it should. The context budget covered one of the three prompts
that embed the retrieved schema. The prompt registry's drift detection
covered the prompts someone had remembered to list. Neither control was
weak. Both were partial, and in both cases nothing measured the gap — so
the fix in each case was a test that derives the required set from the
code rather than from a maintained list.

### Corrected measurement a future session should not re-derive

`config/settings.py` said the usable context window is
`num_ctx / OLLAMA_NUM_PARALLEL` and that budgets should be sized against
half. **Measured on `llama3.1:8b` at `num_ctx=16384`, with `/api/ps`
confirming the served length, that is wrong by 2x.** A ~22,065-token
prompt was processed whole at 15,442 real tokens. A ~50,065-token prompt
came back at 8,194 with the system prompt gone — the probe put a codeword
in the system prompt and the model answered *"There is no codeword."*

So **the shape is a cliff, not a taper**: a prompt is processed whole up
to roughly the full `num_ctx`, and past that it is cut to `num_ctx/2`,
losing the start. The "exactly half" figure in the old comment is the
post-truncation floor, not the admission limit. Both current budgets are
therefore sized against half the real window and leave ~50% of context
unused — conservative in the safe direction, and deliberately left alone,
because raising them changes which blocks reach the model and moves
`docs/EVALUATION_CURRENT.md`'s accuracy numbers.

Real text in this application measures **3.8–5.7 characters per token**
(dense DDL at the low end, prose at the high end), which is why
`CTX-006`'s detector uses a loose ratio rather than trusting
`CHARS_PER_TOKEN = 4`.

### Decisions needed from the product owner

**`CTX-003` — neither routing prompt states any safety invariant.**
`prompts/router.md` and the fallback classifier both receive the question
and the conversation transcript and carry no untrusted-data framing;
`governance_center/safety.py`'s own docstring claims every such prompt
carries it. Bounded — the content is the caller's own, `router_node`'s
RBAC filter is the real control, and a rewritten source query still
passes the validator and the result gate. Not fixed because editing a
live routing prompt changes routing behaviour and routing has no
labelled-corpus accuracy measurement, so the change could not be shown
neutral. **Either** add a framing sentence to both and accept an
unmeasured routing change, **or** record that the two routing prompts
rely on the RBAC filter rather than their own text.

**`CTX-007` — schema retrieval is punctuation-sensitive.** `top selling
products` retrieves 5 tables from `adventureworks`; the same question
with a trailing period retrieves 8, and with a question mark 6. Case and
whitespace do not matter, because the lexical path is already normalised
— it is the embedding query that is raw. This one is genuinely two-sided:
the trailing-period variant pulls in `FactInternetSales`, which for that
question is arguably the *more* correct table, and CLAUDE.md §13
separately records that this exact question is answered badly today. So
normalising to preserve the base behaviour might make retrieval *worse*
on the very question that exposed the bug. **Decide with the benchmark,
not from the code:** normalise the embedded query, re-run
`scripts/run_benchmark`, and keep whichever direction measures better.

### Gap this phase could not close

**`CTX-011` is UNVERIFIED, not passed.** The brief asks for measured
retrieval recall/precision against a golden set.
`docs/retrieval-evaluation.md` defines the criteria and states in its own
opening that wiring them into the harness is follow-up work; **no
labelled fixture set exists**, so there is nothing to measure against. A
human must author a labelled question → required-tables/columns set
first.

### A process note, recorded because it cost real time

Two Claude sessions ran concurrently in the same working tree. The other
session's `git add -A` swept this phase's uncommitted `CTX-006` work into
its own commit (`f4195d5`), and its branch checkout moved `HEAD`
mid-task. No work was lost, but the commit message on `f4195d5` is not
the one written for that change. The remainder of this phase was done in
a separate `git worktree`, which is what made the two sessions
genuinely independent. **If two sessions must share a repository, give
each one a worktree first and stage explicit paths, never `-A`.**

### Two standing traps this phase proved the hard way

**`assert` is not a control.** `python -O` deletes every `assert` from
the bytecode, and three boundaries were relying on one: the four JWT
key checks in `identity/security.py` (where the assert's removal turns a
configuration failure into an opaque **HTTP 500 on every login**),
`mcp_client/trust.py`'s remote-tool trust boundary, and
`mcp_client/protocol.py`'s JSON-RPC newline-framing check. All three now
raise. Narrowing-only asserts are deliberately **kept**, with a
`# nosec B101` naming the real guarantee — the distinction is whether
removing the statement removes a control. Tested in a subprocess, since
`-O` is interpreter start-up state, with a test that proves asserts are
actually stripped first so the rest cannot pass vacuously.

**`identity/models.py`'s docstring is right and mypy is wrong, on
purpose.** Do not "fix" the four SQLAlchemy nullable-column errors by
widening the annotations to `Mapped[X | None]`. The inherited session
did, and `import api.main` then raised
`TypeError: descriptor '__getitem__' requires a 'typing.Union' object
but received a 'tuple'` — the whole application failed to import, which
is precisely what that docstring warns about. They are closed with
line-scoped `# type: ignore[assignment]` instead (`BP-015`).

screenshot.**

real node count) and `nodes` (truncated to three). An early reading of the

### And one that is not new but was confirmed again

**jsdom cannot be trusted to stay silent about what it cannot see.**
`color-contrast` is blind there, which was known. `target-size` is also
blind (every element measures 0x0). But `label-content-name-mismatch`
reports a **false pass**: the exact markup Chrome flagged lands in axe's
`passes` list under jsdom, because the rule needs rendered text. A test
that asked axe about it would have read as evidence of the opposite of the
truth. All three are now disabled in `src/test/axe.ts` with the
measurement behind each, because a disabled rule is visibly absent from
the results whereas an enabled one that cannot evaluate its input reports
a pass that means nothing.

### Post-audit end-to-end run (2026-10-30)

Phase 9's own fixes were verified, and then the application was exercised
end to end against the live stack on a user's report. That run produced
two findings the screen-by-screen audit could not have: both are about
what happens **after** a question is asked, and both were invisible until
the system was driven with a genuinely broken configuration.

`OPS-009` is the sharper of the two, and its shape generalises. The
circuit breaker, the failure classifier and the user-facing error message
each behaved exactly as written; the defect was that **two of them
disagreed about the same event**. `ollama_unavailable_error` correctly
called a 404 "the model is not installed -- pull it", while
`record_outcome` called the same 404 a provider-health signal. One told
the user to pick a different model; the other then refused the model they
picked. Neither function was wrong in isolation, and no test asked whether
they agreed. The fix is therefore not a new rule but a **shared
predicate** -- `_is_model_not_found` is now the single place that decides,
and both callers read it.

The lesson to carry: when one condition drives both a user-facing message
and a control decision, derive them from one function. Two independent
`isinstance` checks of the same exception will drift, and the drift is
silent because each side looks correct on its own.

`OPS-010` is the mundane companion -- the condition was knowable at
startup and nothing said it. Worth noting only because the information was
genuinely already there, in `GET /models`, which is the usual shape of an
operational gap: not missing data, just data nobody surfaced at the moment
it mattered.
